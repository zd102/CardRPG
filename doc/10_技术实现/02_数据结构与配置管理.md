## 设计结论

- 本模块目标：装备、卡牌和效果通过明确的数据关系组合，内容调整可以校验并追溯到来源。
- 技术选择：JSON 为规则配置唯一来源，以 System.Text.Json 读取为强类型 C# 数据对象；Godot Resource 负责图像、音频和场景引用，不重复维护同一份规则数值。
- 配置模板只读，运行时实例和存档分别表达可变状态。选择依据见[技术选型与架构](01_技术选型与架构.md)；具体字段、公式与内容规模仍待填写。

## 配置目录

**角色、属性、装备、词缀、卡牌、效果、敌人和掉落采用什么格式？**

采用按内容类别组织的 JSON，加载后转换为强类型对象并统一校验。表格可在内容量增加后作为编辑入口，但需通过导出流程生成同一份 JSON，不同时人工维护两套数值。文件拆分粒度与编辑工具待原型验证。

**表之间如何通过稳定 ID 引用，如何避免名称变更破坏引用？**

以稳定配置 ID 引用装备、卡牌、效果、敌人和资源；名称仅用于显示。装备实例、战斗卡牌实例和区域对象另有实例 ID。卡牌副本记录配置 ID、实例 ID 与供牌来源；无武器默认牌使用明确的默认来源标识。场景节点路径不作为跨版本的存档标识，具体命名规范待填写。

**配置数据与运行时实例的数据边界是什么？**

| 层级 | 内容 | 约束 |
| --- | --- | --- |
| 配置模板 | 装备需求与供牌清单、卡牌费用、效果参数 | 加载校验后只读，不存当前血量或牌区 |
| 持久实例 | 属性分配、装备实例及穿戴、区域进度 | 引用配置 ID，保存实例差异 |
| 战斗实例 | 本场资源、状态、卡牌副本与牌区顺序 | 各副本唯一，流转时移动实例，不复制配置为可变共享对象 |
| 界面状态 | 选中、悬停、布局、动画进度 | 不作为规则权威状态，不改变配置模板 |

战外卡组由实际穿戴装备及无武器默认规则推导；若允许保存战斗现场，按[存档方案](04_存档读档与版本兼容.md)恢复本场实例。

## 校验与版本

**如何发现重复 ID、无效引用、非法范围和循环依赖？**

加载阶段和构建验证阶段使用同一校验入口：检查重复 ID、引用存在性、必填字段与数量范围，检查禁止循环的引用关系。无武器默认清单必须有效且非空，双手武器按装备实例去重后供牌。错误报告包含文件、内容 ID 和字段，校验失败时不发布该配置集。合法范围及允许的连锁关系仍按玩法细化。

**配置版本、兼容规则与存档版本如何关联？**

分别登记内容配置版本和存档结构版本，存档记录其使用的配置版本。配置 ID 删除、替换或含义改变必须评估迁移；格式兼容不代表规则结果相同。迁移与失败保护见[存档读档与版本兼容](04_存档读档与版本兼容.md)。

**配置修改如何比较差异并定位到受影响内容？**

JSON 与代码一起纳入 Git，提交时检查文本差异、引用校验和受影响规则测试。变更记录使用内容 ID 关联装备、卡牌和效果，不依靠显示名称推断影响。

**填写一条从装备配置到授予卡牌、再引用效果的完整数据链。**

装备实例 → 装备配置 ID → 供牌清单中的卡牌 ID 与张数 → 卡牌配置的费用及效果列表 → 效果处理器。建立战斗牌库时，为各副本生成独立实例并保存装备来源。空槽不供牌；双手武器占用两个手位但只计一件来源；未穿戴武器时另加入默认牌。正式内容 ID 与数值待登记。

## 卡牌循环与装备槽位的数据约束

- 卡牌类型区分行动卡与魔法卡，分别对应行动点和魔法点；具体费用和特殊覆盖规则需配置。
- 默认角色每回合开始抽牌数为 5，首回合相同，不叠加额外开局抽牌；角色回合结束将所有手牌移至弃牌区。抽牌数量为新增抽取数量，不是手牌补齐目标。特殊效果的覆盖参数与优先级待填写。
- 战斗状态需表达抽牌区、手牌和弃牌区的卡牌实例及顺序；洗回时移动实例，不复制卡牌。
- 武器需表达单手／双手占用关系，双手武器即使引用两个手位也只汇总一次卡牌与属性贡献。
- 头盔、身体护甲、手套、鞋子各 1 个位置，戒指 2 个；护符需同时表达最多 4 个位置与当前解锁数量（1～4）。
- 装备 JSON 配置需表达供牌清单、额外属性加成或特效。具体字段与校验实现待填写。

规则来源：[装备部位与穿戴](../03_装备系统/01_装备部位与穿戴.md)、[牌区流转](../04_卡牌系统/03_抽牌手牌与牌区流转.md)。
